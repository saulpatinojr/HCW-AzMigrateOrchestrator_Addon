# Changelog

The engine, rules, CLI and UI components are versioned and released upstream in `saulpatinojr/HCW-MigrateOrchestrator_App`
(see its `CHANGELOG.md`, which also carries the history of the pre-split monorepo). This file tracks the web-front edition only.

## Unreleased

- `core-update.yml` now runs from `main` only, and auto-merge no longer listens to the `bump` job's report. Two High findings from the review of the two-job split (pull request 57, which merged before they were fixed). First, a person with write access could start the workflow by hand on another branch (`gh workflow run --ref <branch>`); the `pull-request` job would then run that branch's `scripts/core-update-pin.mjs` before minting the App token, and a changed script could skip the checks. Now the first step of each job stops the run with an error that names the branch unless it was started on `refs/heads/main`, the `pull-request` job's `if:` also requires `main`, and both checkouts take the exact commit the run was started for (`github.sha`; `create-pull-request` is told `base: main`, which it needs when the checkout is a commit). The `bump` job has no job-level `if:` on purpose, so a refused run shows as failed rather than skipped. Second, the outcome file comes from the job that ran upstream code, so a compromised release could rewrite it to `success` and turn auto-merge on. Auto-merge now depends on the repository variable `CORE_AUTOMERGE` being `true`, the run not being a probe, and the `pull-request` job's own byte-for-byte check passing; it never reads the outcome. GitHub merges only after the "Protect main" ruleset's required checks (`build-test`, `e2e`, `codeql`, `secret-scan`, `dependency-review`) pass on the bump pull request itself. The outcome still picks the label, the title and the body text. So when `CORE_AUTOMERGE` is `true`, a `needs-adaptation` bump also has auto-merge turned on, and merges once its checks pass (normally after someone fixes it on its branch); select **Disable auto-merge** on the pull request to hold one. `tests/security/core-update-app-token.test.mjs` checks both guards. Not run on GitHub yet; see `VALIDATION.md`.
- `core-update.yml` is split into two jobs, so the upstream packages' code never runs on the same machine as the GitHub App key. Before, one job installed the new release (`npm ci` runs the packages' install scripts), ran the tests and then minted the App token, so a compromised upstream release could have changed the checkout or read the token. Now the `bump` job does the install, the tests and the e2e suite with no secret and `contents: read`, and uploads `package.json`, `package-lock.json` and the outcome. The `pull-request` job starts on a fresh machine and runs none of that code: it moves the two URLs with the new `scripts/core-update-pin.mjs` (from the checkout of `main`; Node built-ins only, an exact replacement instead of `sed`), re-locks with `npm install --package-lock-only --ignore-scripts --allow-git=none --allow-remote=root --allow-file=none --allow-directory=root` run by npm 11.20.0 from its registry tarball, checked against a pinned sha256 (the same npm in both jobs), checks the lock (the two release URLs with a sha512 integrity, every other package from the npm registry), and refuses the artifact unless both files are byte-identical to its own, or if it holds anything else. On a refusal it resets the checkout and stops before the token exists. Nothing from the artifact is copied in; the outcome only picks the label and the title. That job's `setup-node` restores no package-manager cache, since the first job could have written one. The refs step also refuses a pinned tag in `package.json` that is not `vMAJOR.MINOR.PATCH`. Tests: `tests/security/core-update-app-token.test.mjs` now checks both jobs, `tests/security/core-update-apply.test.mjs` runs the workflow's own steps against tampered artifacts, and `tests/security/core-update-pin.test.mjs` covers the script. The same split was made in the Cloud Assessor and NetworkEyes add-ons. Not run on GitHub yet; see `VALIDATION.md`.
- `core-update.yml` now refuses an upstream release tag that is not a plain version (`vMAJOR.MINOR.PATCH`, the only form the upstream release workflow publishes) or that spans more than one line. The tag is pasted into a `sed` command and into the step outputs, and GNU `sed` runs a shell command for a crafted tag such as `v9|;e…`, in the job that later holds the App token. A test now runs the guard's own lines against good and hostile tags. Found by an independent review of the same workflow in the Cloud Assessor add-on.
- `core-update.yml` opens its bump pull request with a short-lived GitHub App token (`actions/create-github-app-token`, pinned to v3.3.0; the HCW Main Admin App, installed on this repository: its client ID is the repository variable `HCW_MAIN_ADMIN_CLIENT_ID`, which is not a secret, and its private key is the repository secret `HCW_MAIN_ADMIN_PRIVATE_KEY`, which is never printed; the job no longer runs in an environment) instead of `GITHUB_TOKEN`. The token step names this repository (`repositories: ${{ github.repository }}`) and sets no `owner`, so even an empty value could only fall back to this repository, never to every repository the App is installed on. Why: a pull request opened with `GITHUB_TOKEN` starts no workflow, so the required checks never ran on the first bump pull request and it could not merge. The token is minted for this repository only, with Contents and Pull requests write, after the compatibility check and just before the pull request is opened; `GITHUB_TOKEN` is now `contents: read` only. Because the App's pull request starts this edition's own CI, the "do not trigger other workflows" comment is gone; the compatibility check in the run still decides the label and whether auto-merge is requested. Turning on auto-merge no longer fails the run when the repository setting "Allow auto-merge" is off (the first bump run ended red on exactly that); it warns and leaves the pull request to merge by hand. A manual run with `probe=true` mints the token, makes a read-only call and lists the repositories the token covers (the run fails unless that is this repository only), and opens no pull request and asks for no auto-merge even when a newer release exists, to prove the credential when there is no release to adopt. `tests/security/core-update-app-token.test.mjs` pins all of it (no `GITHUB_TOKEN` passed to `create-pull-request`, the token step first, the HCW Main Admin variable and secret, the token limited to this repository, exactly the two permissions, SHA pins, and none of the old credential names left). To rotate the key, generate a new private key on the settings page of the App (https://github.com/settings/apps), replace the repository secret `HCW_MAIN_ADMIN_PRIVATE_KEY` in every repository that holds the key (this one: https://github.com/saulpatinojr/HCW-MigrateOrchestrator_AddOn/settings/secrets/actions; the App is installed on the four add-on repositories, so check the other three), then delete the old key on the settings page of the App. The settings page can hold several keys, so a separate key per repository lets you revoke one without touching the others. `VALIDATION.md` no longer says the pull requests do not trigger `ci`.
- `.github/workflows/guide-drift.yml` switches on the website's check that this repository's integration guide still says what the website says (website issue saulpatinojr/HCW-HybridCloudWorks#1356). It calls a reusable workflow (a workflow that another repository can call, like a function) from the website repository, pinned to a full commit, and compares the catalogue row pasted into `docs/website-integration/integration-guide.md` with the website's row for `migration`, field by field. It runs on pull requests that touch the guide or this workflow, every Monday at 06:35 UTC and on demand. It holds no secret and has `contents: read` only. To switch it off, delete the file. How to read a failure: https://github.com/saulpatinojr/HCW-HybridCloudWorks/blob/main/docs/runbooks/addon-guide-drift.md
- `docs/whats-new-upstream.md`: an entry says the next core release carries the log redaction fix (upstream pull request 81: sign-in tokens and private keys are now hidden by `redact()`), and the "Current upstream state" table is brought up to 2026-10-25. Documentation only; no code, pin or dependency changes.
- `docs/whats-new-upstream.md`: an entry says the next core release limits one CSV cell to 65,536 characters and fixes slow expressions (upstream pull request 88). Documentation only.
